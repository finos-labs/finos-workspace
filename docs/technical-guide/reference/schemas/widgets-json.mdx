# widgets.json

A backend describes its widgets in a file named `widgets.json`. The file is an object whose keys are widget ids and whose values are widget definitions. This page explains what a definition may contain and how FINOS Workspace builds the schema that defines every accepted key and value. [Widget requests](../protocols/widget-requests.mdx) describes the requests that the web app makes from a definition.

## A definition

A definition must have the keys `name`, `description`, `endpoint` and `type`. It may also have `method`, `category`, `subCategory`, `source`, `showTitle`, `params`, `gridData`, `staleTime`, `refetchInterval`, `dataUpdateDisplay`, `runButton`, `disableRetrievalForCopilot`, `exportable`, `mcp_tool` and `data`. The key `mcp_tool` links the widget to an MCP tool, as [The MCP tool link](../protocols/mcp-tool-link.md) describes. The `data` object always accepts `dataKey`, and some types accept more keys. The types `html` and every plugin type also accept `raw`, which [Widget rows](../protocols/raw-rows.md) describes, and `iframe` accepts `storage`.

The contract is closed. A key that the contract does not define is an error at every depth of the definition. When a definition breaks the contract, the web app leaves the widget out of the catalog and reports the problem together with its JSON pointer. Strings and lists are bounded as well.

## Types

The `type` of a definition decides which component renders the widget and which request methods and parameter locations the widget may use.

| `type` | What renders it | Methods | Where parameters can go |
|---|---|---|---|
| `markdown`, `html`, `newsfeed` and `pdf` | The built-in widgets of the same names. | `GET` and `POST`. | The query, a header or the body. |
| `iframe` | A page that the widget embeds from the endpoint's URL. | `GET`. | The query. |
| A plugin type | The plugin that handles the type, as [About widget plugins](../../../plugins/widget-plugins.md) describes. | `GET` and `POST`. | The query, a header or the body. |

A plugin type exists for an organization when the organization has enabled a plugin that handles it. When two enabled plugins handle the same type, the organization admin's choice decides which of them renders it, and without a choice the plugin with the lowest id wins. A widget whose type nobody handles for the user does not appear in that user's catalog.

A plugin type keeps its own configuration in `data.<type>`. For a type named `plotly`, that is the object at `data.plotly`. The plugin declares the schema of this object as its `definition`, as [Plugin package and manifest](../../../plugins/reference/package-and-manifest.mdx) describes, and the plugin reads the object as the `definition` trait. When a source refreshes, FINOS Workspace copies the object, together with `dataKey`, `rawDataKey` and `rawType`, onto the widgets that are already on dashboards.

## One schema for each organization

The API composes one JSON Schema (draft-07) for each organization. It starts from the kit, which contains the base keys, the rules of each built-in type and the rules for plugin types, and which FINOS Workspace generates from the web app's Zod contract. It then adds the `definition` of every plugin type that the organization has enabled.

```jsonc
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "$id": "urn:workspace:widgets-json:<etag>",
  "type": "object",
  "additionalProperties": { "$ref": "#/definitions/Widget" },
  "x-types": ["markdown", "html", "newsfeed", "pdf", "iframe", "<plugin type>"],
  "definitions": {
    "Widget": { "oneOf": [{ "$ref": "#/definitions/Widget_markdown" }, "..."] },
    "Widget_<type>": { "type": "object", "additionalProperties": false, "required": ["name", "description", "endpoint", "type"], "properties": { "type": { "const": "<type>" }, "data": { "$ref": "#/definitions/Data_<type>" }, "...": "..." } },
    "Data_<type>": { "type": "object", "additionalProperties": false, "properties": { "dataKey": {}, "<plugin type>": "the plugin's definition" } },
    "PluginConfig_<plugin type>": "the handler widget's settings, closed",
    "ParamDef": "one closed branch per param type",
    "McpTool": "the mcp_tool object"
  }
}
```

Each `Widget_<type>` definition is complete on its own, so the schema works with any draft-07 validator. To produce readable errors, a validator should first check the widget's `type` against `x-types` and then validate the widget against that single branch.

**The schema is closed.** In the composed schema every object has `additionalProperties: false` or a defined value schema, every string has a `maxLength`, an `enum`, a `const` or a `pattern`, and every array has `maxItems`. A test walks the kit and fails when it finds anything open. The same walk runs on a plugin's `definition` when the plugin is discovered, and a definition that is not closed and bounded blocks the version and names the offending node.

**The API serves the schema.** The route `GET /app/widget-plugins/widgets-schema` answers for the signed-in user's organization, and a superuser may pass `?entity=` to ask for another one. The answer carries an `ETag`, and the route returns `304` for a matching `If-None-Match` header. When the plugin feature is off, the schema contains only the built-in types. The web app fetches the schema together with the plugin list and hands it to the worker that loads backends. A new `$id` makes the worker validate the connected backends again.

## Checks in code

JSON Schema cannot express every rule of the contract. The function `contractProblems` checks the remaining rules after the schema check passed. It verifies that:

- every `{name}` in `endpoint` or `optionsEndpoint` names a declared parameter, and that a parameter that fills a path placeholder declares no `in` and takes one value;
- every `paramName` is unique, and every `$name` in `optionsParams` or in `mcp_tool.args` names a declared parameter;
- the inputs of a form are unique, and every placeholder in a form names an input or a parameter;
- at most one parameter has the role `fileSelector`, and every cron expression is valid;
- no header parameter uses a header that the backend connection needs for its credentials, and no query parameter uses a query name that the connection needs;
- the value of `mcp_tool.mcp_server` names a server in the backend's `apps.json`.

## Instance-level schemas

An MCP client creates or changes a widget through the FINOS Workspace MCP, and each of these calls takes two argument objects. The tool `get_widget_schema` returns a closed schema for each of them:

- The schema `data_args_schema` has one property for each declared parameter. A parameter with static options takes an enum of those options. A number also accepts a numeric string. A date accepts `YYYY-MM-DD` or `$currentDate` with a modifier. A `multiSelect` or `multiple` parameter accepts a list or a comma-separated string. FINOS Workspace ignores a value that the schema refuses and issues a warning that names the key.
- The schema `ui_args_schema` has the keys `name`, `description` and `source`, plus `innerTab` and `gridData` for `create_widget`. It also has the keys of the component that renders the widget: `text` for markdown, `html` for HTML, and `config` for a plugin widget. The `config` object follows the plugin's settings and is stored in `storage.plugin.config`. An undefined key or a wrong value refuses the whole call with `invalid_request` and names each path, and a dry run returns `valid: false` together with the problems.

Every parameter row also carries `in`, whose value is `path`, `query`, `header` or `body`, and `get_widget_schema` returns the widget's `method` and `mcp_tool` as well.

## apps.json templates

A layout item of an `apps.json` template can set a plugin widget's configuration in `state.storage.plugin.config`. When a backend loads, FINOS Workspace reports an app and leaves it out if one of its layout items sets this configuration for a widget of a built-in type, or sets a value that the plugin's settings refuse (`PluginConfig_<type>`). The report names the path of each problem. When a user opens an app, FINOS Workspace merges the template's state into the widget's storage, and the plugin widget reads the configuration from there.

## Where the schema is built

The file `frontend/src/lib/types/widgetsContract.ts` holds the strict Zod objects, the header tables, each type's methods and parameter locations, and the reserved query names. The file `widgetsSchemaKit.ts` turns the contract into the kit. The command `node scripts/generate-widgets-schema.ts`, which you run from `frontend/`, writes the kit to `backend-api/backend/api/widget_plugins/widgets_schema_kit.json`, and a Vitest test fails when the committed kit is out of date. The module `backend-api/backend/api/widget_plugins/widgets_schema.py` composes the schema, and `python -m scripts.compose_widgets_schema` prints a composition offline. A pytest test fails when the web app's fixture `frontend/tests/mocks/widgets-schema.json` is not the composer's output.

The script `backend-api/backend/scripts/generate_app_builder_specs.py` generates the pages that the app-builder resources of the MCP servers serve. These pages hold the type catalog, the response of each type, the widget fields, and the parameter fields and header-name rules. The script writes them from the kit between `<!-- generated:<name> -->` markers, and a pytest test fails when a page is out of date. The pages list only the built-in types, because the plugin types differ between organizations. They point to `workspace://specs/widgets-json-schema` instead, which the user's FINOS Workspace tab answers over the bridge with the organization's composed schema.
