# About sessions and tokens

Workspace has several kinds of credential, and each one exists because the others would be wrong for its job. A person signs in once and gets a session. The browser then needs to prove that session to the API, to the agent and to the MCP servers, and an outside AI host needs a way in that never involves a password. This page explains the credentials and why they differ. [Agent authentication](../reference/protocols/agent-authentication.mdx) gives the exact headers and limits.

## The session

When a user signs in, the API creates a session and sends the browser one cookie, `__Host-ws_session`. The cookie holds a random token, and the API stores only a hash of it, so a copy of the database is not a set of working sessions. A session lasts <SettingConstant name="sessionLifetimeSeconds" unit="days" />, or <SettingConstant name="rememberedSessionLifetimeSeconds" unit="days" /> when the user chooses to be remembered, and a user has one session at a time: signing in on another device ends the earlier session.

The cookie is built so that a script cannot take it. It is `HttpOnly`, so no script on the page can read it, which means that a flaw in a widget or a browser extension cannot copy it. It is `Secure`, so the browser sends it over HTTPS only. It is `SameSite=Strict`, so the browser leaves it out of any request that another site starts. Its name begins with `__Host-`, which makes the browser refuse the cookie unless it was set over HTTPS, with the path `/` and without a `Domain` attribute, so that the cookie belongs to one exact host and a neighboring subdomain cannot plant one of its own. The API also requires every request to carry the header `X-Workspace-Client: web`, and it refuses a request from an origin that the deployment has not allowed. A page on another site cannot add that header to a request without first asking the API for permission, which the API gives only to its allowed origins. Together these keep other sites from using the session even if the browser would send the cookie.

## Why the agent cannot use the session

Ines is a different service, usually on a different origin, so the browser does not send it the cookie, and Workspace would not want it to. A service that held the session could act as the user for as long as the session lasts, and the agent passes the user's text to a language model, which is the wrong place to keep a master key. Workspace therefore gives the agent a smaller credential, the agent token. The browser asks the API for one with its session, and the token lives for <SettingConstant name="agentTokenLifetimeSeconds" unit="min" /> or for the rest of the session, whichever is shorter. The browser keeps it in memory and never in browser storage, and renews it when less than <WebAppValue of="agentTokenRenewSeconds" unit="min" /> remain. The API stores only a hash of the token. The token works on three routes of the API, which let the agent learn who the user is, ask what the user's roles allow and add to the user's usage, and it works nowhere else. When the user signs out, or the session ends for any other reason, the tokens end with it.

The cost of this design is a small delay in noticing a change. Ines remembers who a token belongs to for <EnvDefault name="INES_AUTH_CACHE_SECONDS" /> seconds by default, so a user who signs out can still send a question for a few more seconds. A deployment that cannot accept the delay sets the time to zero, and Ines then asks the API on every request.

## Who vouches for the agent

The agent asks the API to record a user's usage and to say what the user may do, and the API must be sure that the caller is the agent and not a user who wants to reset their own count. The agent proves itself with a second credential, the metering token, which it sends beside the user's token. The token is a JWT that the operator creates with the deployment's signing secret, so users cannot create one, and it expires, <SettingConstant name="meteringTokenDefaultLifetimeSeconds" unit="days" /> after its creation by default, so that a leaked token does not last forever. An operator who lets it expire has to mint a new one, and until then the agent cannot answer questions, because it can no longer count or authorize them.

## Credentials for outside AI hosts

An AI host outside the app, such as a desktop assistant, connects to the Workspace MCP server and acts on the user's dashboards through a tab that the user has open. It has no browser session, and a password in the configuration file of a desktop tool would be worse than a token. A user therefore creates a personal access token in the app. The token begins with `ws_mcp_`, it is shown once at the moment of creation, and the API stores only its hash, the time of its last use and whether it has been revoked. It has no expiry, and it works until the user revokes it, so a user who no longer trusts a host revokes its token and nothing else changes. Each token acts for the user who created it and can do only what that user's tab can do.

## Other short-lived credentials

A few more credentials exist for single purposes. A password reset is a link that an admin generates for a user. It works once, it expires after <SettingConstant name="passwordResetLifetimeSeconds" unit="hours" />, and the API stores only its hash. A two-factor enrollment starts from a separate cookie, `__Host-ws_totp`, that lives for <SettingConstant name="totpEnrollmentLifetimeSeconds" unit="min" /> and lets the user finish setting up an authenticator but do nothing else. A call from the API to a plugin's backend carries a call token and the secrets that its route names, and the plugin's frame holds none of them, as [About the widget plugin security model](widget-plugin-security.md) explains.

## The pattern

The credentials follow one rule: each is the weakest thing that can do its job, and none of them is kept where a script can read it. The session proves the person to the API. The agent token lets a language-model service ask three questions of the API on the person's behalf for up to <SettingConstant name="agentTokenLifetimeSeconds" unit="min" />. The metering token lets that service report usage. The personal access token lets an outside tool use a tab, and it can be taken back. Storing only hashes means that a leak of the stores does not leak the credentials.
