# About the architecture of FINOS Workspace

FINOS Workspace is a web application that is made of a few cooperating services, and one idea explains most of how they fit together: the browser is the hub. The user's dashboards live in the browser while the user works with them, and the browser talks directly to the services that each need to hear from it. The services talk to each other far less than one might expect. This page describes the parts, what each of them is responsible for, and why the connections run the way they do.

## The parts

The **web app** is a single-page application written in React. A web server delivers it as static files, together with a small `config.js` that tells the app where its API and its agent are. The app holds everything that the user sees: the dashboards, the widgets and the chat with the Copilot.

The **FINOS Workspace API** is a FastAPI application and the system of record. It owns the accounts, the sessions, the roles and their permissions, the saved dashboards and apps, the uploaded files, the connections to data backends and the settings of each organization. It answers the web app's requests, it checks who is allowed to do what, and, together with the worker, it is the only part that talks to the database. It also hosts the FINOS Workspace MCP server at `/mcp`, and it forwards the browser's calls to the MCP servers that users connect.

The **worker** runs the jobs that should not hold up a request. It tidies up old dashboard versions and uploads that no widget uses, it updates shared files after a share changes, it refreshes each user's usage totals every five minutes, and at midnight UTC it resets the daily counts of Copilot questions. The API puts the jobs on a queue in Valkey, and the worker takes them from there.

The **stores** are a relational database, Valkey and file storage. The database, which can be MySQL, PostgreSQL or SQLite, holds the accounts, roles, dashboards and settings. Valkey, which speaks the Redis protocol, holds the job queue and short-lived state, such as the tokens that the agent uses and the messages that let several API processes cooperate. File storage holds uploads on a folder or on an AWS, Azure or Google cloud bucket.

**Ines** is the built-in agent, the service behind the Copilot. It is a separate service on Node that talks to a language model, and it has a second process, the **Ines MCP server**, that offers it tools for searching the web and the documents in a chat. Ines does not store dashboards and it cannot reach a user's data. It receives what the browser sends with each question.

A **data backend** is a service that the organization or a third party runs and that serves widgets. It describes its widgets in a `widgets.json` file, and the web app asks it for each widget's data. Backends are not part of FINOS Workspace, but every dashboard depends on at least one of them. A **plugin backend** is a small restricted service that a widget plugin ships for work that cannot run in the browser, and only the API calls it.

One more piece runs once and then goes away. When a deployment starts, an initialization job upgrades the database schema and creates the first organization and administrator, and only then do the API and the worker start.

## Why the browser is the hub

A design in which every request went through the API would be simpler to draw, and many applications are built that way. FINOS Workspace sends data requests from the browser to the backends instead, and it sends questions from the browser to Ines. The reason is that the backends and the agent are meant to be run by other people than the team that runs the API. A bank can connect a backend that its own data team operates, behind the bank's own network rules, and the API never has to see the data. The same holds for the agent: whoever runs it needs no access to the user's dashboards, because the browser decides what each question carries.

This is the same shape as a business intelligence front end that queries its data sources directly, and as an editor whose AI assistant asks the editor to run tools. The cost is that the browser has to be trusted with what it holds, and the design pays for that with limits. The browser holds the credentials of a backend connection because it needs them to make the calls, and the API keeps them encrypted in the database. The session cookie that proves who the user is cannot be read by scripts, and the agent never receives it. The agent receives a token that expires after <SettingConstant name="agentTokenLifetimeSeconds" unit="min" /> instead, as [About sessions and tokens](sessions-and-tokens.mdx) explains. Ines never calls an MCP server or the FINOS Workspace itself, because the browser performs every such call, as [About how the Copilot answers](how-the-copilot-answers.md) explains.

## What each part trusts

The API trusts nothing that arrives without a valid session. It also checks that a request comes from an origin that the deployment allows, so that a page on another site cannot use a user's session. Ines trusts the API's answer to the question of who a token belongs to, and by default it asks again at most every <EnvDefault name="INES_AUTH_CACHE_SECONDS" /> seconds. The tools of the Ines MCP server that keep a chat's state trust only calls that carry the agent's signature for that chat. A data backend decides for itself what its connection's credentials may read. A plugin's code runs in a sandboxed frame that has no access to the page or to the user's session, as [About the widget plugin security model](widget-plugin-security.md) explains.

## What scales how

The web server is static and scales trivially. The API keeps its state in the database and in Valkey, so a deployment can run as many API processes as it needs. When a user's browser tab is connected to one process and a call arrives at another, the processes pass the call through Valkey. Ines can also run as several replicas, but only when it has Valkey: it then shares who is signed in, how much of a user's daily share is left and which turn of a conversation is under way. Without Valkey it keeps that state in its own process and has to run as one replica. [Transports](../reference/transports.mdx) lists every channel with its port and framing, for the person who has to open them.
