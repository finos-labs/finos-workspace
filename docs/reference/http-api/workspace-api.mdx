# Workspace API

The Workspace API is the FastAPI application in `backend-api/backend` that the web app, the worker, the Workspace MCP server and the admin tools talk to. This page lists its routes, grouped by the tag that each router gives them. For each route it shows the method and path, a summary, the parameters and the request and response types. The request and response types link to [Workspace API schemas](workspace-api-schemas.mdx).

The API does not serve interactive documentation. It sets `docs_url`, `redoc_url` and `openapi_url` to `None`, so this page is the reference. The summary of a route is derived from the name of its function, so it names what the route does but does not describe it in detail.

## How requests are authenticated

A signed-in browser holds a session in the HttpOnly, secure and same-site cookie `__Host-ws_session`, and the web app marks its requests with the header `X-Workspace-Client: web`. A request that cannot be authenticated receives the status 401 with the detail "Could not validate credentials". The API sets every response to a request that carries credentials with `Cache-Control: no-store`, so that no cache keeps it. Some routes need more than a session, and they answer 403 when the user lacks the role. The routes under `/admin` need a user of type Admin, and the routes under `/plugins` need a superuser.

Every HTTP and WebSocket request must come from an allowed origin. The API allows the origins that are listed in `BACKEND_CORS_ORIGINS` and the origins that match `BACKEND_CORS_ORIGIN_REGEX`. It refuses any other request, including a request without an `Origin` header, with the status 403 and the detail "Requests must come from an allowed origin", and it closes a WebSocket with code 1008. The paths `/health` and `/healthz` are the only exceptions.

Routes that apply a rate limit allow <SettingConstant name="rateLimitDefault" /> for each client address by default, and a few sensitive routes allow <SettingConstant name="rateLimitFew" />. A request that carries a valid service token in the header `X-Workspace-Authorization` is exempt from the limits when the deployment turns that exemption on with `RATE_LIMIT_EXEMPT_ENABLED`.

The page is generated from `backend-api/backend/tests/fixtures/openapi.json`, which a test keeps equal to the document that `app.openapi()` builds. The document leaves out `/metrics`, because that route exists only when the `PROMETHEUS` setting is on, and it serves the Prometheus metrics.

## admin

The routes under `/admin` let an organization's admin manage its users and invitations, password and two-factor resets, roles and their permissions with the audit log, apps, theme settings and presets, and the organization's own settings. They require a user of type Admin.

<ApiTag tag="admin" schemaPage="/reference/http-api/workspace-api-schemas" />

## app

These routes are under `/app` and carry no other tag. They serve the signed-in web app with the user's access and two-factor settings, the Copilot's chats, keys, access and tokens, the organization's theme settings, the user's MCP servers and other per-user data.

<ApiTag tag="app" schemaPage="/reference/http-api/workspace-api-schemas" />

## app-dash

The routes under `/app/dash` synchronize the user's dashboards, show their versions, and manage how a dashboard is shared with other users and with the organization.

<ApiTag tag="app-dash" schemaPage="/reference/http-api/workspace-api-schemas" />

## app-data-connectors

## widget-plugins

These are the widget plugin routes. Superuser routes are under `/plugins`, organization admin routes are under `/admin/plugins`, member routes are under `/app/widget-plugins`, and the backends' data route is under `/internal/plugin-broker`. [Plugin lifecycle and administration](../plugins/lifecycle.mdx) explains how they fit together.
