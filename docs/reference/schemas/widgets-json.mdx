# widgets.json

A backend lists its widgets in a file named `widgets.json`. The file is an object. Each key is a widget's id, at most 128 characters long, and each value is a widget definition. The file may also have the keys `$schema`, the address of a schema that editors use to check the file, and `$id`, an identifier of the file. Both are strings of at most 2048 characters. [Widget requests](../protocols/widget-requests.mdx) describes the requests that the web app makes from a definition.

The fields below come from the JSON Schema that the backend's exporter writes to `backend-api/backend/reference-data/widgets_schema.json` for the built-in types `markdown`, `html`, `newsfeed`, `pdf` and `iframe`, and for one plugin type, which is shown as `<type>` and stands for the type of every plugin that an organization has enabled. A note such as `for html` means that only widgets of that type have the field. [The JSON Schema file](#the-json-schema-file) shows the schema as validators read it.

## The data key

The object `data` describes the response of the endpoint, so that FINOS Workspace knows where the data is in it and what to do with it. The keys `dataKey`, `rawDataKey` and `rawType` are listed under Widget definition. A widget of a plugin type also has the key `data.<type>`, which is named after the type and whose schema is the `definition` of the plugin.

FINOS Workspace checks the widget against the plugin's `definition`. A widget that fails the check is left out of the catalog, and the problem is reported with its JSON pointer. The plugin module receives the checked object as its `definition` trait, as [Plugin module contract](../plugins/module-contract.mdx) describes, and the AI Agent reads the `definition` when it builds widgets of the type. [Plugin package and manifest](../plugins/package-and-manifest.mdx) describes how a plugin writes the `definition`. When a source refreshes, FINOS Workspace copies `data.<type>`, together with `dataKey`, `rawDataKey` and `rawType`, onto the widgets that are already on dashboards.

These examples come from the reference backend in `docs/examples/reference-backend/widgets.json`.

```json

    "name": "News feed widget",
    "description": "Invented articles about invented companies, filtered by category",
    "category": "Reference backend",
    "subCategory": "Widget types",
    "type": "newsfeed",
    "endpoint": "newsfeed_widget",
    "gridData": {
      "w": 20,
      "h": 16
    },
    "source": "Invented sample data",
    "params": [
      {
        "paramName": "category",
        "type": "text",
        "label": "Category",
        "description": "Show the articles of one category",
        "value": "all",
        "options": [
          {
            "label": "All",
            "value": "all"
          },
          {
            "label": "Business",
            "value": "business"
          },
          {
            "label": "Technology",
            "value": "tech"
          }

      }
```

```json
    "subCategory": "Widget types",

      "w": 20,

  }
```

## Types

The `type` of a definition decides which component renders the widget and which request methods and parameter locations the widget may use.

| `type` | What renders it | Methods | Where parameters can go |
|---|---|---|---|
| `markdown`, `html`, `newsfeed` and `pdf` | The built-in widgets of the same names. | `GET` and `POST`. | The query, a header or the body. |
| `iframe` | A page that the widget embeds from the endpoint's URL. | `GET`. | The query. |
| A plugin type | The plugin that handles the type. | `GET` and `POST`. | The query, a header or the body. |

The `data` object always accepts `dataKey`, and some types accept more keys. The types `html` and every plugin type also accept `raw`, which [Widget rows](../protocols/raw-rows.md) describes, and `iframe` accepts `storage`. The key `mcp_tool` links the widget to an MCP tool, as [The MCP tool link](../protocols/mcp-tool-link.md) describes.

A plugin type exists for an organization when the organization has enabled a plugin that handles it. When two enabled plugins handle the same type, the organization admin's choice decides which of them renders it, and without a choice the plugin with the lowest id wins. A widget whose type nobody handles for the user does not appear in that user's catalog.

## Validation

The schema defines every key at every depth of a definition, and it bounds every string and list. A key that the schema does not define is ignored: the web app loads the widget without the key and lists the key, with its JSON pointer, under the backend's unrecognized fields. Any other problem leaves the widget out of the catalog and is reported together with its JSON pointer.

JSON Schema cannot express every rule of the contract. The function `contractProblems` checks the remaining rules after the schema check passed, and the web app reports each problem with its JSON pointer. This table comes from running it on a definition that breaks each rule.

## The schema that the API serves

The route `GET /app/widget-plugins/widgets-schema` answers for the signed-in user's organization, and a superuser may pass `?entity=` to ask for another one. The answer carries an `ETag`, and the route returns `304` for a matching `If-None-Match` header.

- The schema is the one above plus what the enabled plugins add. Its `x-types` array lists the types that are available. When the plugin feature is off, the schema contains only the built-in types.
- Each `Widget_<type>` definition is complete on its own, so the schema works with any draft-07 validator. To produce readable errors, a validator should first check the widget's `type` against `x-types` and then validate the widget against that single branch.
- The schema is closed. Every object has `additionalProperties: false` or a defined value schema, every string has a `maxLength`, an `enum`, a `const` or a `pattern`, and every array has `maxItems`. The web app reads a failed `additionalProperties: false` as a key to ignore, unless it falls inside a `oneOf` or an `anyOf` that no branch matched.
- A plugin's `definition` must be closed and bounded in the same way. FINOS Workspace checks it when it discovers the plugin, and a definition that is not closed and bounded blocks the version and names the offending node.
- The web app fetches the schema together with the plugin list and hands it to the worker that loads backends. A new `$id` makes the worker validate the connected backends again.
