# Iframe widget protocol

An iframe widget embeds a page from another server. By default the page is just shown, but a page can also talk to Workspace, and then it can offer several widgets to the dashboard and the Copilot, show parameter controls in the widget's header, and receive the backend connection's credentials. The page and Workspace talk through `window.postMessage`. This page describes the messages, the order in which they are sent and the rules that decide whether Workspace accepts a message. The host side is `frontend/src/components/Widgets/Helpers/useIframeProtocol.tsx`, and the messages are defined in `frontend/src/types/iframeProtocol.ts`.

## How a conversation starts

The embedded page starts the conversation. It sends a `workspace-connect` message to its parent window, which lists the widgets that the page can supply and, optionally, the parameters that it understands. Workspace remembers the window and the origin that the message came from, and it uses them as the address of every later message to the page. A page that never sends `workspace-connect` is shown as an ordinary iframe, and none of the features below apply to it.

When the handshake succeeds, three things happen:

- The widgets in the manifest become sub-widgets of the iframe widget. The Copilot lists each one under an id of the form `<iframe widget uuid>::iframe::<widgetId>`, and it can ask for their data.
- The parameters in `params` appear as controls in a row below the widget's navigation bar, unless the widget's own definition already declares a parameter with the same name.
- If the backend connection has header credentials, Workspace sends them to the page in a `workspace-auth` message.

## Messages from the page to Workspace

Every message is an object with a `type` field.

| `type` | Fields | Meaning |
|---|---|---|
| `workspace-connect` | `widgets`, a list of objects with `widgetId`, `name`, `dataType` (`table` or `markdown`) and optional `description` and `category`. `params`, an optional list of parameter definitions. | The page announces the widgets that it supplies and the parameters that it understands. |
| `workspace-data` | `widgetId`, `dataType`, `data`, and an optional `columns` list. For `table`, `data` is an array of row objects. For `markdown`, `data` is a string. | The page answers a `workspace-request`. |
| `workspace-error` | `widgetId` and `error`, a string. | The page cannot answer a `workspace-request`. The request fails with that message. |
| `workspace:widget-params:update` or `workspace:params:update` | `params`, an object of `name: value`, or the pair `paramName` and `value`. | The page changes parameter values. |

A parameter definition in `params` has a `paramName` and a `type` of `text`, `number`, `date` or `boolean`. It may also have a `label`, a `description`, a default `value` as a string, a list of `options` that each have a `label` and a `value`, and for numbers the limits `min`, `max` and `step`.

In a parameter update, a value may be a string, a number, a boolean or `null`, or a list of those. Workspace turns every value into a string. It joins a list with commas, leaves out `null` items in a list, and turns a single `null` into an empty string. A message that has both `params` and `paramName` applies both.

Workspace validates each message against its schema. A message that does not match is ignored, and a warning appears in the browser console that names the problem, for example "check your widget manifest".

## Messages from Workspace to the page

| `type` | Fields | Meaning |
|---|---|---|
| `workspace-request` | `widgetId`, or `null`. | Workspace asks the page for the data of one widget. The page should answer with `workspace-data` or `workspace-error`. Workspace gives up after <WebAppValue of="iframeRequestTimeoutMs" unit="ms" /> and fails the request with a time-out. |
| `workspace-params-update` | `params`, an object of `name: value` strings that holds every current parameter value, including `theme`, which is `light` or `dark`. | A parameter value changed, so the page should update what it shows. Workspace also sends the message after the handshake, and again when the user changes a control, when a parameter that the widget shares in a group changes, and when the site's theme changes. |
| `workspace-auth` | `headers`, an object of header names and values. | The backend connection's header credentials, which the page can attach to its own requests. |

## Which messages Workspace accepts

Workspace accepts a protocol message only when it comes from the iframe that belongs to the widget. A message qualifies when its source is the iframe's window, when it is the window that sent the `workspace-connect` message, or when it comes from a frame nested inside the iframe, up to eight levels deep. This lets a page forward messages from an inner frame, for example when the visible content is a second frame.

Workspace sends credentials with `workspace-auth` only when the origin of the window that connected equals the origin of the iframe's address. A page that connects from any other origin does not receive them. Workspace sends the message again whenever the credentials change. The credentials never appear in the iframe's URL.
