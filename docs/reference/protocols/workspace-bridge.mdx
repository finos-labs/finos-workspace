# FINOS Workspace bridge protocol

The bridge is the connection between the FINOS Workspace MCP server and a signed-in FINOS Workspace tab. This page specifies how a tab opens a session, the messages on the WebSocket, the commands that the tab runs and the limits of the bridge. [MCP Companion](../../features/mcp-companion/index.mdx) explains how the bridge works.

| Side | Code |
|---|---|
| API | `backend-api/backend/routers/app/workspace_mcp/` and `backend-api/backend/workspace_mcp/models.py` |
| Web app | `frontend/src/components/AI/WorkspaceBridgeConnectionManager.tsx` and `workspaceBridgeProtocol.ts` |

## Opening a session

A tab opens a bridge session in two steps. Before the steps, the user must sign in, and the MCP Companion must be on in the tab.

1. The tab sends `POST /app/workspace-mcp/bridge/session/start` with its `client_name`. It can also send the `current_dashboard_id` and the `current_tab_id` that it shows.
   - The API answers with the new `session`, which contains a `session_id`.
   - The answer also contains a `websocket_url` in the form `wss://<api host>/app/workspace-mcp/bridge/ws?session_id=<session id>`.
   - The tab waits a maximum of <BridgeValue of="limits.sessionStartTimeoutMs" unit="ms" /> for the answer.
2. The tab opens that WebSocket.
   - The browser sends the cookie of the web session with the request.
   - The API also requires an allowed origin, as [FINOS Workspace API](../http-api/workspace-api.mdx) describes.
   - The API closes the socket with code <BridgeValue of="constants.closeCode" unit="raw" /> in these conditions:
     - The cookie is missing or not valid.
     - The session id is not a session of the signed-in user.

Each user has a maximum of one active bridge session. A new session replaces the old session:

- The API closes the old socket.
- The commands that wait for the old socket fail with the message "<BridgeValue of="constants.sessionReplacedMessage" plain />".

The API keeps a started session for <BridgeValue of="constants.sessionTtlSeconds" unit="s" />. A tab that does not connect in that time must start a new session.

When the API accepts the socket, it sends the first event, `session_ready`. The session is then live.

While the socket is open, the API checks every <BridgeValue of="constants.sessionCheckSeconds" unit="s" /> that the web session that opened the socket is still active. When the web session stops, the API does these two things:

- It closes the socket with code <BridgeValue of="constants.closeCode" unit="raw" />.
- It fails the waiting commands with the message "<BridgeValue of="constants.sessionEndedMessage" plain />".

## Messages over the WebSocket

Each message is a JSON object with a `type` field. The API checks the messages that the browser sends. The API closes the socket with code <BridgeValue of="constants.closeCode" unit="raw" /> when the web session stops.

## Commands

The `command_request` message contains one of <BridgeValue of="counts.sent" plain /> commands. Each command has two fields:

- `command` gives the name of the command.
- `request_id` identifies the call.

The table below gives the other arguments of each command. The tab accepts <BridgeValue of="counts.accepted" plain /> commands in total. Only the Agent sends the command <BridgeList of="agentOnlyCommands" />. The tab runs it with the same handler, but it never goes over the WebSocket. ## Limits and failures

| Limit | Value |
|---|---|
| Time that the API waits for a command result | <BridgeValue of="constants.commandTimeoutSeconds" unit="s" />. After this time, the result is `ok: false` with the error code `timeout` and `retryable: true`. |
| Liveness | The tab sends a ping every <BridgeValue of="limits.heartbeatIntervalMs" unit="ms" />. Each ping keeps the session present for <BridgeValue of="constants.presenceTtlSeconds" unit="s" />. The tab closes a connection that gives no answer for <BridgeValue of="limits.heartbeatTimeoutMs" unit="ms" />. |
| No connected tab | When no tab is connected, the tool call fails with the message "<BridgeValue of="constants.noBrowserMessage" plain />". A command can wait when the tab disconnects, or when a new session replaces the tab. That command fails with the error code `unavailable` and `retryable: true`. The message is "<BridgeValue of="constants.disconnectedMessage" plain />", or the message for a replaced session. |
| Reconnects | When the tab loses the connection, it tries again a maximum of <BridgeValue of="limits.maxReconnectAttempts" plain /> times. The first wait is <BridgeValue of="limits.reconnectBaseDelayMs" unit="ms" />. Each subsequent wait is two times longer. After the last attempt, the tab reports that the connection failed. |
| Repeated requests | The API keeps the results of the last <BridgeValue of="constants.completedResultsMax" plain /> requests. When a command comes again with the same `request_id`, it gets the stored result. The command does not run a second time. |

The API runs more than one worker process. The socket of the tab is open on only one of them. When a tool call comes to a different worker, that worker sends the call to the worker with the socket. The workers use the shared Redis-compatible store for this. The result comes back in the same way. The AI tool does not need to know which worker holds the tab.
