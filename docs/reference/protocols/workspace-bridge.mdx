# FINOS Workspace bridge protocol

The FINOS Workspace MCP server does not hold a user's dashboards. The dashboards live in the user's browser, so every tool of the server works by sending a command to a FINOS Workspace tab and waiting for the tab's answer. The channel between the server and the tab is the bridge. This page describes how a tab opens a bridge session, the messages that the API and the tab exchange over a WebSocket, the commands that the tab executes, and the limits that apply. The server side is `backend-api/backend/routers/app/workspace_mcp/` and `backend-api/backend/workspace_mcp/models.py`, and the browser side is `frontend/src/components/AI/WorkspaceBridgeConnectionManager.tsx` and `workspaceBridgeProtocol.ts`. The tables on this page are generated from the Python models and from the constants of the two sides, and tests keep the data equal to the code.

## Opening a session

A tab opens a bridge session in two steps. The user must be signed in, and the tab must have the companion mode of the FINOS Workspace MCP turned on.

1. The tab sends `POST /app/workspace-mcp/bridge/session/start` with its `client_name` and, optionally, the `current_dashboard_id` and `current_tab_id` that it shows. The API answers with the new `session`, which holds a `session_id`, and with a `websocket_url` of the form `wss://<api host>/app/workspace-mcp/bridge/ws?session_id=<session id>`. The tab waits at most <BridgeValue of="limits.sessionStartTimeoutMs" unit="ms" /> for the answer.
2. The tab opens that WebSocket. The browser sends the web session cookie with the request, and the API also requires an allowed origin, as [FINOS Workspace API](../http-api/workspace-api.mdx) describes. The API closes the socket with code <BridgeValue of="constants.closeCode" unit="raw" /> when the cookie is missing or invalid, or when the session id does not belong to the signed-in user.

Each user has at most one active bridge session. Starting a new session replaces the old one: the API closes the old socket and fails the commands that were waiting for it with the message "<BridgeValue of="constants.sessionReplacedMessage" plain />". The API keeps a started session for <BridgeValue of="constants.sessionTtlSeconds" unit="s" />, so a tab that does not connect within that time has to start a new session.

When the socket is accepted, the API sends the first event, `session_ready`, and the session is live. While the socket is open, the API checks every <BridgeValue of="constants.sessionCheckSeconds" unit="s" /> that the web session that opened it is still alive. When the web session has ended, the API closes the socket with code <BridgeValue of="constants.closeCode" unit="raw" /> and fails the waiting commands with the message "<BridgeValue of="constants.sessionEndedMessage" plain />".

## Commands

The `command_request` message carries one of <BridgeValue of="counts.sent" plain /> commands. Every command has a `command` field that names it and a `request_id` that identifies the call, and the table lists the other arguments of each command. The tab accepts <BridgeValue of="counts.accepted" plain /> commands in all. The command <BridgeList of="agentOnlyCommands" /> comes only from the agent, which runs it through the same handler in the tab, and it never travels over the WebSocket. ## Limits and failures

| Limit | Value |
|---|---|
| Time that the API waits for a command result | <BridgeValue of="constants.commandTimeoutSeconds" unit="s" />. After that the result is `ok: false` with the error code `timeout` and `retryable: true`. |
| Liveness | The tab pings every <BridgeValue of="limits.heartbeatIntervalMs" unit="ms" />, and each ping refreshes the session's presence for <BridgeValue of="constants.presenceTtlSeconds" unit="s" />. The tab closes a connection that has not answered for <BridgeValue of="limits.heartbeatTimeoutMs" unit="ms" />. |
| No connected tab | When no tab is connected, the tool call fails with the message "<BridgeValue of="constants.noBrowserMessage" plain />". A command that is already waiting when the tab disconnects or is replaced fails with the error code `unavailable` and `retryable: true`, and with the message "<BridgeValue of="constants.disconnectedMessage" plain />" or the one for a replaced session. |
| Reconnects | After a lost connection the tab retries up to <BridgeValue of="limits.maxReconnectAttempts" plain /> times. The first wait is <BridgeValue of="limits.reconnectBaseDelayMs" unit="ms" />, and each later wait is twice as long. The tab then reports that the connection failed. |
| Repeated requests | The API remembers the results of the last <BridgeValue of="constants.completedResultsMax" plain /> requests, so a command that is sent again with the same `request_id` receives the stored result and does not run twice. |

The API runs several worker processes, and the tab's socket is open on only one of them. A tool call that arrives at another worker is forwarded to the worker that holds the socket through the shared Redis-compatible store, and the result comes back the same way, so the MCP client does not need to know which worker holds the tab.
