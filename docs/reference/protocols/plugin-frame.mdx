# Plugin frame protocol

This page describes how the host, which is the Workspace page, and a plugin's frame talk to each other. The protocol runs at runtime version <PluginValue of="versions.runtime" plain /> and AFM version <PluginValue of="versions.afm" plain />. The host defines the messages in `frontend/src/plugins/protocol.ts`, and the frame's shell is `frontend/src/plugins/shell/shell.js`. The message tables on this page are generated from the schemas in `protocol.ts`, and a test keeps the data equal to the code.

## The frame

A plugin's widget runs in an iframe that the host creates with these properties:

- **Sandbox.** The frame is an `iframe` whose `sandbox` attribute is <PluginValue of="shell.sandbox" />, whose `referrerpolicy` is `no-referrer` and whose document is in `srcdoc`, and nothing else. It has an opaque origin, so it cannot reach the parent page and it has no `localStorage`, `sessionStorage`, IndexedDB or cookies. Its requests carry `Origin: null`. The sandbox never includes `allow-same-origin`, popups, top navigation, forms, modals or downloads. The frame's Content Security Policy is described on [Plugin frame policy](../plugins/frame-policy.mdx).
- **A private channel.** The host answers only the <PluginValue of="shell.ready" /> message that comes from the frame's own window, and it answers by handing that window one end of a `MessageChannel`. From then on the frame talks only over its port. The host ignores messages that arrive through `window.postMessage`, it identifies the sender by the port and never by a field inside a message, and it validates every message against a schema.
- **No ambient authority.** The user's session never enters the frame. The host makes every authenticated call, and a request that the policy lets the frame make carries no credentials. Secrets stay on the server.
- **Verified code.** The host fetches the plugin's files with the user's session and checks the SHA-256 of each file against the approved digest. It then sends the bytes into the frame, which evaluates them from a `blob:` URL. A remote `script-src` origin, which only a superuser can add, lets in code that this check does not cover.
- **Confinement to the card.** A frame draws only inside its own card. A notice from a plugin is shown as plain text, it is rate limited, and it is labelled with the plugin's name. Links that a plugin opens go through the external-link confirmation.

## Starting a frame

A frame starts in five steps:

1. The host creates the frame with the composed policy and waits for a message of type <PluginValue of="shell.ready" /> from that frame's window.
2. The host posts a message of type <PluginValue of="shell.port" /> to the frame and transfers one end of a new `MessageChannel` with it. The shell runs its canary and answers with a `hello` message.
3. The host checks the `hello` message. Every canary check must have passed, the runtime and AFM versions must be the host's own, and the frame's document must not be readable from the page. When any of these conditions fails, the host ends the frame and the card shows "Plugin sandbox unavailable" with the check that failed. A frame that is not a proper sandbox never receives any code.
4. The host fetches the files and verifies them against the approved digest, and then it sends a `load` message. A file that fails its digest ends the frame as an integrity failure.
5. The shell evaluates the module and runs `initialize` and then `render`, as [Plugin module contract](../plugins/module-contract.mdx) describes, and it sends `loaded`. From then on the host pushes traits and answers commands.

The canary runs before any plugin code is in the frame. It checks that `self.origin` is `"null"`, that `localStorage`, `sessionStorage`, `indexedDB.open` and cookies are unavailable, and that reading `parent.document` throws. For every directive that the policy denies, it also triggers a probe that must raise a violation. The probes are a `fetch` and an image request to a reserved `.invalid` host, a call to `new Function` when eval is not approved, and an inline script. WebKit raises no event for a refused `eval`, so the canary accepts the `EvalError` that WebKit throws as proof.

## Messages from the frame

Every message has a field `t` that names its type. A message of any other form, or a message that fails its schema, counts as a protocol violation.

<PluginGuestMessages />

An `invoke` message calls a command, which [Plugin permissions and commands](../plugins/commands-and-permissions.mdx) lists. A `csp` message reports a blocked request, as [Plugin frame policy](../plugins/frame-policy.mdx) describes.

## Messages from the host

<PluginHostMessages />

When the host refuses an `invoke` message, the `error.name` of its answer is one of <PluginList of="commandErrors" or />. The `member` of a `call-export` message is one of <PluginList of="exportMembers" or />.

## Limits

The host enforces the following limits on the frame:

| Limit | Value |
|---|---|
| Size of one message from the frame | <PluginValue of="limits.maxGuestMessageBytes" unit="bytes" />, counting buffers, strings and keys. |
| Size of one export | <PluginValue of="limits.maxExportBytes" unit="bytes" />. |
| Rate of messages from the frame | About <PluginValue of="limits.GUEST_MESSAGE_RATE.perSecond" /> messages per second, with bursts of up to <PluginValue of="limits.GUEST_MESSAGE_RATE.burst" />. |
| Commands that wait for an answer | At most <PluginValue of="limits.MAX_PENDING_COMMANDS" />. |
| Violations that end the frame | <PluginValue of="limits.VIOLATION_LIMIT.count" /> within <PluginValue of="limits.VIOLATION_LIMIT.windowMs" unit="ms" />. A message over the rate or size limit, a message outside the schema, and a message whose handling fails each count as one violation. |
| Liveness | The host pings every <PluginValue of="limits.PING_INTERVAL_MS" unit="ms" /> and ends a frame that misses <PluginValue of="limits.MISSED_PINGS" /> pings in a row. |
| Loading | `initialize` has <PluginValue of="limits.LOAD_TIMEOUTS_MS.initialize" unit="ms" /> and `render` has <PluginValue of="limits.LOAD_TIMEOUTS_MS.render" unit="ms" />. |
| Navigation | A second `load` event of the iframe means that the frame navigated itself, and the host ends it. |
| Policy reports | At most <PluginValue of="limits.MAX_REPORTS_PER_FLUSH" /> reports every <PluginValue of="limits.REPORT_INTERVAL_MS" unit="ms" />. |

The host creates a plugin widget's frame when its card comes near the viewport, and it releases the frame when the card is scrolled far away or its tab is not active.
